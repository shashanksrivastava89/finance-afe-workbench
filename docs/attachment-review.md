## 2. Friction patterns (addressable)

| # | Pattern | Evidence | Treatment (wave) |
|---|---|---|---|
| P1 | **Band-boundary blindness** — preparers/approvers must know when a value crosses an approval band | Case C: $25,600 is $600 over the M1-only band → tri-signer chain | Deterministic band + named-chain calculation on every case; instant "who must sign" answer (**W1**, already built) |
| P2 | **Version churn before signature** — redline rounds circulate by email; risk of acting on a stale version | Case C filename "dea redlines-**Latest**"; 4 people involved pre-signature | Case timeline with document versions; long-term: pre-submission checks shrink redline rounds (**W1** case model, **W2** checks) |
| P3 | **Approval evidence arrives as DocuSign certificates** — machine-readable signer names, emails, roles, timestamps, envelope IDs | Cases A, B, C all carry Certificates of Completion | **Deterministic certificate parsing** → auto-verify signers vs the required chain from the matrix; flag gaps ("A1 signature missing for $25,600") (**W1**) |
| P4 | **AFE number assignment is an email round-trip** | Case A subject; Case B form prints "To be added by CS or Asset team" | Number issuance/registry inside the tool (pending Q4 numbering scheme) (**W1**) |
| P5 | **Template + fill-quality variance** — US multi-page vs APAC/Demo 1-pager (product table, local currency); budget section misuse | Case B (INR, both Addition & Supplemental filled), Case C (budget $0/blank) | Extraction normalizes all variants to one schema; deterministic validation flags misuse for FA review (**W2** extraction, **W1** checks on extracted data) |
| P6 | **RRC path has no AFE** — contract-driven, different document set | Case D | Type-aware completeness checklists (Normal / Demo / RRC); case types drive required-document lists (**W1** static checklists, **W2** AI suggestions) |
| P7 | **Manual SAP cost cross-checks** — FA screenshots MM03 standard costs into the package | Case A screenshots | Keep evidence attach now; SAP cost lookup automation is a Phase-2 candidate (**W3**) |
| P8 | **Everything is email** — intake, clarification, chasing, returning the completed package all happen in the shared mailbox, hand-written per case | All cases; RTR_FA mailbox | Mailbox-integrated cases (Dev Mailbox now, Graph later) + **AI-drafted, FA-approved follow-up emails** with case context (**W1** dev-mailbox intake, **W2** drafting) |
| P9 | **Mixed digital/scanned documents** | Case D approval PDF has **no text layer**; all other PDFs do | Tiered extraction: text-layer path (majority) + OCR/vision path (scans) (**W2**) |
| P10 | **Duplicate intake** — the same request lands twice | Case B received twice, byte-identical | Dedupe on attachment hash / envelope ID at intake (**W1**) |

## 3. What this means for extraction (the pointer-1 question)

- **ColPali-style visual RAG is the wrong tool here.** ColPali/visual retrieval excels at *finding* relevant pages across a large corpus. Our problem is *single-document structured extraction against a known schema* (Form 00070 Rev 6 variants + DocuSign certificates + CPQ/contract headers). No retrieval step exists to optimize.
- **A dedicated Document Intelligence model is optional, not required, to start.** Evidence: 5 of 6 sampled PDFs carry full text layers (Excel-exported or system-generated). The tiered approach:
  - **Tier 0 (deterministic):** original `.xlsx` attached → parse the workbook directly (named cells; 100% fidelity). DocuSign Certificate pages → deterministic text parse (signers, timestamps, envelope ID).
  - **Tier 1 (majority):** text-layer PDFs → layout-aware text extraction → **LLM structuring** against the AFE JSON schema, returning per-field values + confidence + source-page anchors. FA reviews side-by-side and corrects.
  - **Tier 2 (scans, e.g. Case D approval):** page → image → **multimodal LLM** extraction (same output schema). If evals show table-fidelity gaps, add **Azure AI Document Intelligence `prebuilt-layout`** (a small S0 resource; none exists in the sandbox today) in front.
- **Model availability (verified via Azure MCP, subscription `GIT - Sandbox - Development`):** two Azure OpenAI accounts are live and usable now — `ResumeScreenerOAI` (eastus: **gpt-4.1** GlobalStandard 250K TPM + text-embedding-3-large) and `dev-task-analyze` (westus3: **gpt-4.1** + text-embedding-3-small). gpt-4.1 is multimodal → covers Tiers 1 and 2 with zero new infrastructure.
- **Managed open-source preference:** no Foundry project exists yet; standing one up unlocks managed OSS (Phi-4-multimodal / Mistral-class). Workload is light (tens of documents/day), so cost is not the driver — accuracy is. Recommendation: ship the PoC on the existing gpt-4.1 deployments, build a small labeled eval set from these four real packages, then trial an OSS model behind the same `aiClient` seam and switch if it holds accuracy.
- **Guardrails (pointer 6):** Azure OpenAI provides content filtering, regional data residency, and no-training-on-inputs by policy; the tenant already runs private-endpoint patterns (privatelink DNS zones present). App-level guardrails we design in: data never leaves the Acme tenant, every AI output is a *suggestion* requiring FA confirmation (human-in-the-loop), per-field confidence thresholds gate auto-acceptance, and the audit trail records AI-suggested vs FA-confirmed values plus every AI-drafted email before/after FA edits.

## 4. Wave prioritization (pointer 8 applied)

- **Wave 1 — deterministic, lowest-hanging:** case creation from mailbox (Dev Mailbox) or upload · dedupe (P10) · band + named-chain calculation (P1, built) · DocuSign certificate parse + approval-gap flags (P3) · arithmetic/classification checks on entered or extracted data (P5-checks) · AFE number registry (P4, pending Q4) · type-aware static checklists (P6) · tracker/dashboard (built).
- **Wave 2 — the painful patterns, AI-assisted:** tiered document extraction with review UI (P5, P9) · completeness suggestions (P6) · follow-up email drafting with case context, FA-approved sends (P8) · redline-round reduction via pre-checks (P2).
- **Wave 3 — post-review:** SAP cost cross-check automation (P7) · requester-facing surfaces · Graph mailbox live send/receive · broader SAP integration per the existing Phase-2 seam.
