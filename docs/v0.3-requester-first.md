## 1. What changed, in the stakeholders' words

The Early Review (2026-09-02, Judithmelanie · Jarrod · Ebony · Lyndsay · Imogen · Manaia) reversed the
premise the PoC was built on. Verbatim:

> **Manaia:** "I don't think this was the intent. The intent was that people are able to create
> AFEs using this tool. We don't want to build a tool wherein the Fixed Assets team is required to
> upload the information for their checking purpose. The starting of the AFE — creating the AFE
> form itself — should happen on the tool."

> **Jarrod:** "This tool is definitely for the Fixed Assets team, but the users will be across the
> globe. The project team, IT team, whoever is going to raise an AFE in their department — all
> those people will be the users, and the starting point will be them."

> **Imogen:** "We want to digitalize that PDF process. It should be paperless; all signs should be
> in digital form."

> **Manaia:** "Once a project manager initiates the form and fills out the cost centre, the
> workflow should get auto-triggered to the people responsible for approving. They should be able
> to approve, reject, ask a question, or send it back for rework."

> **Manaia:** "The FA checks — whether an approver is missing, all of that — will by default
> become a control when you fill out the form using the tool. Those checks go away automatically.
> Then the Fixed Assets team performs their **judgmental check**, which is not to be done through
> machine, and issues the AFE and creates the IO."

> **Manaia:** "Don't follow this process flow. That was the FA team's internal process flow. The
> things that happen in SAP will continue to happen in SAP."

> **Judithmelanie:** "These steps can be utilised for AUC confirmations… if in the second phase we
> implement something in SAP, all these things you have shown may be useful."

So: the FA workbench built to date is **Phase 2 material**, not wrong — but the product starts
somewhere else entirely. Everything below is written with no backward-compatibility obligation.

## 5. The template, decomposed into the wizard

The Larson template is seven sheets. A first-time requester sees ~30 fields, a 10-year cash-flow
model, a SOW cost sheet and two questionnaires all at once. That is the overwhelm to design out.

| Template sheet | What it holds | Where it goes in the wizard |
|---|---|---|
| **AFE Form** | Header (cost centre, type, dates, location, title, description), totals, Financial Summary (CapEx / OpEx / Cloud CapEx in USD + local currency), Budget block, Supplemental block, Assist question, Controllership Review, Project Approvals, Financial Approvals ladder | Steps **1 Start**, **2 Money**, **6 Review**; the approvals ladder is *rendered from the matrix*, never typed |
| **Project Details** | Description · Scope · Justification · Alternatives · EHS impact · New equipment? · Buy-vs-lease done? (+ "checked the 925 Surplus Area?" from Reference) | Step **3 Story** — one prompt at a time, with a sentence of guidance each |
| **Financials (NPV, ROI & PB)** | 10-year CapEx/OpEx/Cloud lines, recurring benefits, depreciation, 23 % tax, 10 % discount → NPV, ROI, payback | Step **4 If it applies** — only when triggered (Q31); pre-filled from Step 2; the model computes, the requester enters benefits only |
| **Cloud CapEx** | Four yes/no questions → OpEx-vs-CapEx conclusion | Step **4** — only when Cloud CapEx > 0 or type is software; the conclusion is shown, not asked |
| **Facilities** | SOW: A&E · Construction · Network/Telecom · FF&E · Services, each line Cap/Exp, contingency %, tax % | Step **4** — only for construction / fit-out types; totals flow back to Step 2 |
| **DataVal** | Asset life (14) · Asset class (35) | **Not asked of the requester** — asset class is FA's call at AS01 |
| **Reference** | Project types (16) · Locations (~150 sites) · contingency / tax % lists · Y/N prompts | Dropdown sources; location **defaults from the cost centre's plant** |

**Field types the wizard enforces** (Manaia's list): numeric (amounts, years), alphanumeric
(title ≤ 40 chars — the SAP description limit; project code), dropdown (cost centre, type,
location, currency), yes/no (budgeted, supplemental, assist, new equipment, buy-vs-lease,
surplus checked), dates (finish ≥ start), free text with guidance (the five Story prompts).

## 6. Design principles for the requester — B2C, not B2B

The first pass (a left progress rail, three side cards of explanation, ~9 fields per screen)
was rejected as *"a traditional legacy app styled template."* The requester is a consumer of
this product, often a first-timer, and the bar is a consumer app: win them.

1. **Journey on top, full width for the answer.** A six-segment stepper across the top
   (What · Who pays · How much · Why · Quote · Review) — tappable, animated, reads as
   progress. No side rails; the content column gets the screen.
2. **One question per screen, 1–3 controls, one line of hint.** The question is set at
   34 px; inputs are 64 px tall; the primary action is a single 56 px button. If a screen
   needs a paragraph to explain itself, the screen is wrong.
3. **Consequences are chips, not panels.** Every downstream effect of an answer — *Mark
   Lawson will sign* · *Location set from this cost centre* · *Under $25k — Mark is your only
   approver* — appears as a coloured chip directly under the answer that caused it, the
   moment it is given.
4. **Three questions decide everything.** What · which cost centre · roughly how much drive
   the approver chain, the location, the division and which optional sections exist. The
   optional sections (NPV model, software questionnaire, construction sheet) are never shown
   unless triggered; the requester is told, in one line, that they were skipped.
5. **Nothing computed is typed.** Total = Σ lines, band = f(total), chain = matrix lookup,
   location = plant default, quote total = read from the PDF.
6. **Colour with intent.** Brand green anchors progress, selection and the primary action;
   blue chips carry facts; yellow carries what-happens-next. Not monochrome; not decorative.
7. **Fluid.** Steps slide in (~280 ms), segments fill, chips lift on hover, the CTA lifts on
   hover. Autosave is a word in the header, not a button. Enter advances.
8. **The same wizard on a phone.** 390 px, one column, 56 px targets — a requester can
   start an AFE from the shop floor.
9. **Review is the AFE.** Three compact cards (What · Who pays · How much), the *why*, the
   chain as chips, one button: *Send for approval*. Sent state shows the rail of what happens
   next and asks nothing more.
10. **Approvers decide on a phone.** One screen, four actions, 44 px targets minimum.

## 7. Architecture and approach

### What survives (and its new job)

| Built in v0.2 | New role |
|---|---|
| `chainBuilder` + `refData.BANDS` + approver matrix | The **live router** (R22). Needs name → mailbox (Q37) and SAP sync (R23) |
| `checklist.js` presence rules | **Form validation at entry** (R17). What remains for FA is the judgmental list (R27) |
| `caseBuilder.buildSapEntry` KO01 sheet | The **Issue AFE** step, unchanged (R28) |
| `aucReview.js`, roll-forward, `chaseGroups`, IO drill-in | Step ⑤, unchanged (R35); chasing gains a **scheduler** (R33) |
| Document Intelligence extraction | Optional only: prefill from a legacy AFE during transition; read a quote total to save typing (R21). No longer a control — the wizard is |
| Postgres write-through store, readiness gate | **Draft autosave** and the AFE record of truth |
| Personas / act-as, contrast work, UX rules | Two new personas: Requester, Approver; the B2C design language applies to every screen (R40) |
| `docusignCert.js` deterministic certificate parser | **Verifies** what DocuSign Connect reports on the completed envelope |
| Tracker | Becomes the **project page** once the SAP extract lands (R30) |

### What is new

- **AFE aggregate** with a real lifecycle: `draft → submitted → in_approval → returned → approved → issued → in_construction → capitalized` (+ `rejected`, `withdrawn`). Approvals snapshotted at submit — SOX evidence — and a **rework** creates a new round rather than editing history.
- **Wizard** as its own screen family (`public/app.js` split is now warranted — still no build step).
- **Approver decision** endpoint set: `approve / question / return / reject`, each audited with identity + timestamp.
- **AFE Form PDF generation** (`pdf-lib`, Q42) and the **DocuSign envelope** — create with the chain as sequential signers and attachments as separate documents; Connect webhook (or polling) for status; completed envelope stored on the AFE (§8c).
- **Notification outbox → real delivery**: Graph `Mail.Send` as `RTR_FA` or Power Automate (Q35). Deep links back into the tool.
- **SAP inbound**: scheduled file drop → `imports` (matrix, budget, PO lines). Existing import route generalises.
- **Chase scheduler**: monthly job over the SOX population (already computed by `aucReview`).

### Phases

| Phase | Scope | Gate |
|---|---|---|
| **A — Request → Issue** | Wizard with validation at source · live routing · **AFE Form PDF + DocuSign envelope** · in-tool question / send-back · FA judge & guided SAP keying · notifications via outbox | Present to management for approval (Manaia's ask); Aiden session settles the form rules |
| **B — Track** | SAP extract (per-IO budget / actual / commitment / PO lines) · project page · status updates · automated SOX chase | Euan × SAP team on the file transfer; PMs (Sayeenath / Troy / Anaru) co-design |
| **C — Hardening** | Graph `Mail.Send` · matrix auto-sync · DocuSign-parity decision (Q30) · ADC onboarding with SSO · relational schema | IT approvals |

### Performance and responsiveness (the brief said *key*)

- **One draft document, partial writes.** Each wizard step PATCHes only its fields, debounced
  ~500 ms, optimistic — typing never waits on the network. p95 save-ack budget: 300 ms.
- **Reference data is local.** Cost centres (1,197), locations (~150), types (16) load once,
  cached with an ETag; the cost-centre typeahead is client-side and instant.
- **Chain preview is server-authoritative but debounced** (250 ms) with a skeleton; submit
  re-derives it — the preview can never be the record.
- **No full-screen re-render, ever.** Steps swap in place (`toggleSection`/`patchSection`
  discipline from v0.2), transitions ≤ 180 ms, scroll preserved.
- **Budget:** first paint < 1 s on App Service (one HTML + one JS file, no framework), step
  change < 100 ms, approver decision round-trip < 500 ms.
- **Phone-first for approvers** (390 px), 44 px targets, one primary action per screen.

## 8b. Validation at source — can we? Yes, with three honest caveats

The rules are implemented as data in `lib/domain/afeRules.js` and proven by
`tools/smoke-afe-rules.js` against the Larson template: it catches the 41-character title
(SAP keeps 40), a finish date before start, a quote covering 33 % of the estimate, *budgeted*
with no amount, *supplemental* with no original IO, and it derives the band (M1 for $7,915;
M1 + A1 + A2 + A3 for $240K) and the optional sections. 15 checks, deterministic, no model.

| Rule | How | Complexity | If it gets complicated |
|---|---|---|---|
| Mandatory fields; types (numeric / alphanumeric / dropdown / yes-no); title ≤ 40 | Schema on the field | trivial | — |
| Finish ≥ start; amounts ≥ 0; budgeted ⇒ amount; supplemental ⇒ original IO | Cross-field rules | trivial | — |
| **Breakup = total** | The requester never types a total — it is computed | trivial | Rule still runs for the import path (R21) |
| Cost centre exists and is Active | Lookup in the SAP matrix extract | easy | Reports *pending* if the extract is stale, never a false block |
| Approver chain resolves | Band engine over the matrix (built) | easy | **Caveat 1 — sending** needs signer emails (Q37); the matrix has names only |
| **Quote covers ≥ 60–70 %** | Requester enters the quote total (and vendor) as a field; arithmetic does the rest | easy | Reading the total off the PDF is optional DI prefill — if it misreads, the typed value wins. Threshold is Q34 |
| Optional sections appear when triggered | `conditionalSections()` | easy | **Caveat 2 — the NPV threshold is unknown (Q31)**; the rule reports *pending* until set |
| **NPV / ROI / payback model** | Re-implementing the template's cash-flow sheet (depreciation, 23 % tax, 10 % discount) | **moderate — the one genuinely complicated rule** | Alternatives, in order of preference: (a) keep it *outside* the wizard — the requester attaches the Excel Financials sheet for large projects and the Finance Business Partner reviews it, exactly as the template's own note says ("consult with your Finance Business Partner"); (b) implement the model server-side and reconcile against the Excel on the sample set before trusting it; (c) collect only the inputs (benefits by year) and compute NPV/ROI/payback with a small, tested function. Recommend (a) for Phase A, (c) for Phase B |
| Duplicate of an open request | Same cost centre + similar title/amount in the last 90 days | easy | Warn, never block |
| Budget availability in SAP | Needs the per-IO extract | Phase B | Until then: *budgeted?* is the requester's assertion, shown to FA |

**Caveat 3 — the form as a control surface.** Today the Excel enforces nothing (the Banjo
form's Title row is blank; the amount typed in three places can disagree). Moving the
controls to the wizard means the *only* way to raise an AFE is the wizard — the legacy
template must be retired, or every rule has a bypass. Manaia's framing supports this; it
needs saying out loud to the business (Q44).

## 8c. The Filled AFE Form and the DocuSign envelope

**What today's output actually is.** The Banjo PDF (11 pages) is the Excel workbook printed
to PDF — *AFE Form* (p. 1), *Project Details* (p. 2), *Financials* (pp. 3–4, mostly empty
rows), *Cloud CapEx* (p. 5) — followed by six letter-size pages of **pasted SAP screenshots**
with no text layer, the last one cut off. Then DocuSign added its Certificate of Completion
on signing. Nothing on it is machine-checkable except by OCR — which is why v0.2 needed
Document Intelligence at all.

**What the tool generates instead.**

```
Envelope
 ├─ Document 1  AFE Form.pdf            page 1  AFE Form (template layout, all fields, AFE NO blank,
 │                                               Financial Approvals table with a DocuSign anchor per band row)
 │                                       page 2  Project Details
 │                                       page 3+ only the optional sheets this AFE triggered
 ├─ Document 2  Larson_Quote_QX700.pdf  the quote, as uploaded — searchable, complete
 ├─ Document 3…                          further attachments, as uploaded
 └─ (DocuSign appends)                   Certificate of Completion on completion
Signers, sequential:  M1 → A1 → A2 … per the resolved chain; Controllership / Project Approvals rows when triggered
```

- **Generation.** Server-side, with `pdf-lib` (pure JavaScript, no native code) — a **third
  runtime dependency** after `express` and `pg`, which under the ADC rules needs the same
  scrutiny `pg` had (Q42). The alternative that needs no dependency — the browser's print
  dialog — cannot produce the envelope's base document, so it is not an alternative here.
- **What the requester sees.** The review step renders the generated PDF itself (browser
  native viewer), not an HTML approximation. Change anything → regenerate → same view.
- **Routing.** Signers and order come from the band engine; each band row on the form
  carries an anchor string so signatures land on the printed table, exactly where they land
  today. Approver *emails* are the dependency (Q37).
- **Status back.** DocuSign Connect (webhook) or polling → `sent → delivered → signed → completed
  / declined / voided` on the AFE; the completed envelope's combined PDF and certificate are
  stored on the AFE. Our existing deterministic certificate parser (`docusignCert.js`)
  becomes a **verification** of what DocuSign reports, not a substitute for it.
- **Questions and rework.** DocuSign offers *decline* but not a conversation. *Ask a
  question* pauses the envelope (the tool holds routing; the requester answers in-tool);
  *send back* voids it and the wizard reopens at the changed step; resubmission creates a
  new envelope. Signatures already collected on a voided envelope are not reused (Q38).
- **What FA receives.** The same combined PDF they receive today — plus, for the first time,
  every field as data. The judgmental check works from the data; the PDF is the evidence.

**Dependencies to secure now:** a DocuSign account and integration key for the tool (Q41);
Connect webhook reachability to App Service (or fall back to polling); signer emails (Q37).
