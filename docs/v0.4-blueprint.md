## 1. What the 3 Sep session changed

Aiden-Mulqueeny Crilly raises every IT AFE for project managers across NA, APAC and EMEA. His walk-through showed the
process as it is really run — and it is not "requester fills the form". It is a **coordinator** who takes a PM's
description, adds everything finance needs, works out who must sign from the SAP matrix *plus* rules the matrix does
not know, builds the DocuSign envelope by hand, chases signatures, asks FA for the IO number, and keeps a tracker of
budget, commitment and actual per internal order for PMs who have no SAP access.

The consequences for the product:

| Before this session | After |
|---|---|
| Requester fills the wizard and sends | Requester fills the wizard; a **coordinator** (where the division has one) classifies, completes and sends. *Prepared By* on the form is the coordinator. |
| Approvers = SAP matrix levels for the band | Matrix is the **minimum**. Add **pre-approvers** (printed in *Project Approvals*), **override** signers (Vrishti Aguirre for all IT), **additional** finance partners, **charge-to owners**, **controllership** above $1 M, **CC-only** recipients. |
| One person per level | **One person, one signature** — the matrix names the same person at several levels in 2,342 of 2,561 rows. |
| SoD implicit | **Hard block**: preparer, requester, coordinator never sign their own AFE. |
| FA re-checks the form by hand | FA's checks run **at source**; FA gets a **red-flag digest drafted into their inbox**, never auto-sent; **matrix drift** is detected for them. |
| One AFE → one IO | One AFE → **parent + child IOs per country/site**; cost lines declared in the wizard; budget moves between IOs. |
| Prefill by Document Intelligence | **No AI anywhere** (Shashank, 2026-09-04): typed values, deterministic rules, generated documents. |

## 4. Domain model

Storage is the existing JSONB document store (`lib/repos/pgStore.js`, write-through, read-from-memory). Each
collection below is one `collection` prefix. Field names are the contract between routes, domain and UI.

### 4.1 Collections

`users` · `afes` · `routings` · `envelopes` · `ios` · `orgRules` · `budgetPots` · `directory` · `matrix` ·
`snapshots` · `budgetRows` · `ioMaster` · `poLines` · `tracker` (AuC recon lines, kept) · `notifications` (outbox)
· `attachmentsMeta` (+ `attachments` bytea) · `auditEvents` · `jobs`.
Removed: `cases`, `documents`, `mailMessages`.

### 4.5 Stored vs derived

**Stored:** AFE fields; routing snapshots and recipient decisions; envelope events and stored documents; IO registry
and budget moves; extract snapshots; org rules and pots; waivers and acknowledgements; outbox rows (including the
digest text FA saw); audit.
**Derived at read time (never stored):** validation result, red flags, matrix drift, chain preview, FA judgment
row states, KO01 keying sheet, AUC flags and review, per-IO figures, pot KPIs, reminder due-ness.

## 5. Behaviour

### 5.1 Lifecycle

`stateMachine.js` keeps `applyTransition(repos, ctx, afe, action, payload)` and the `TRANSITIONS = {action: {from,
allowed, run}}` shape; the table is rewritten.

States: `draft → submitted → in_approval ⇄ on_hold → approved → fa_review → issued → tracking → capitalized → closed`;
side states `returned`, `rejected`, `withdrawn`.

| Action | From → to | Allowed | Effects |
|---|---|---|---|
| `submit` | draft, returned → `submitted` (division has a coordinator) else → `in_approval` | requester, preparer | `validate()` must have no `block`; without a coordinator, `send` runs inline |
| `send` | submitted, draft, returned → `in_approval` | coordinator of the division, or requester/preparer when none | `buildRouting`, refuse without `emailsConfirmed`, render PDF, create envelope (real or simulated), notify first recipient |
| `question` | in_approval → `on_hold` | current recipient | thread entry; clock note |
| `answer` | on_hold → `in_approval` | requester, preparer, coordinator | resolves thread; re-notifies |
| `send_back` | submitted, in_approval, on_hold → `returned` | current recipient, coordinator | voids envelope; pending recipients `superseded`; wizard reopens at `payload.step` |
| `recipient_signed` | in_approval → in_approval; last signer → `approved` → auto `fa_review` | system (poll/webhook) or current recipient when simulated | marks recipient; on completion stores combined PDF + certificate, verifies recipients vs snapshot, notifies FA |
| `decline` | in_approval → `rejected` | current recipient | voids envelope |
| `withdraw` | draft…on_hold, returned → `withdrawn` | requester, preparer, coordinator | voids envelope if any |
| `fa_return` | fa_review → `returned` | FA | reason required; re-route only if the financial fingerprint changed |
| `fa_record_io` | fa_review → `issued` | fa_preparer | judgment ticks; every `block` flag cleared or acked; drift acked; parent `io`; `afeNo = ioNumber`; notify requester **and** coordinator |
| `add_child_io`, `move_budget` | issued, tracking → `tracking` | FA | child IOs; ± budget moves |
| `capitalize`, `close` | tracking → capitalized → closed | fa_preparer / fa_checker (four-eyes) | as today |

Non-state mutations, each audited with before/after: draft `PATCH` (draft/returned only), `fa_reclassify` (FA's one
edit right), `waive_rule`, `ack_flag`, `ack_drift` (requires an `email_approval` attachment when the owner changed),
`confirm_emails`, `clone` (new AFE for another region with region-specific fields cleared).
**Supplemental** = `POST /afes/:id/supplemental` → new AFE `kind: supplemental`, `supplementalOf` set; routing basis
per `refData.SUPPLEMENTAL_BASIS` (Q39; default `new_total`).
**Reminders** (`reminders.js`, R54): recipients `pending` whose `notifiedAt`/last `remindedAt` is older than
`REMINDER_DAYS` (3) → outbox rows + `remindedAt` stamp; DocuSign envelopes carry their own `notification.reminders`.

### 5.2 Chain builder — `chainBuilder.buildRouting({afe, matrixRow, orgRules, users, directory, original})`

1. **Basis** — sum of `money.lines` (or class amounts); supplemental adds the original approved total when `new_total`. USD only.
2. **Levels** — `requiredLevels(basis)` over `refData.BANDS` (cumulative).
3. **Pre-approvers** — `orgRules kind:"pre_approver"` scoped to `afe.costCenter` or `matrixRow.levels.M1.name`; `printRow:
   project_approvals_n`, `group` from the rule; first in order.
4. **M1**, then **charge-to owner** (from `afe.chargeTo`; slotted after the row the owner *actually* signs at once
   dedupe has run — A1, not M1, when the owner is named at both), then the **A-levels** in band order, then **additional**
   signers (coordinator-added, each labelled with the band row it signs), then **controllership** when total or labour
   > $1 M (`after_matrix`, Q33), then **override** rules for `afe.division` — Erik is added when the band would not
   reach him; authority = highest matrix level he holds; above it `aboveLimit: include` ("signs for visibility") or `skip`.
5. **Dedupe by person** (R45): the same normalised name/email appearing at several rows keeps one recipient at the
   highest row; the others print "(signs above)".
6. **Segregation of duties** (R44): requester, preparer, coordinator (emails + `matrixNames`) → `sod_blocked`; for a
   matrix role the next higher level not already present stands in; none available → `send` blocked. Audited.
7. **Emails** (R60): `users.matrixNames` → `directory` → `First_Last@example.com` (flagged `guessed`) → coordinator
   confirms or types on the routing screen; typed values are learned into `directory` with the AFE id. Any unconfirmed
   email keeps the routing at `preview`.
8. **CC** (R58): requester, FA mailbox, `afe.ccRecipients`, `orgRules kind:"cc"` at `routingOrder = last + 1`.
9. **Explanation** — one line per recipient and rule; warnings for blank matrix cells; rendered as the requester's chips
   and the coordinator's routing review.

### 5.3 Validation at source — `afeRules.js`

- Fields carry `step`, `owner: requester|preparer`, `requiredWhen(a)`; the R50 mandatory set is `costCenter`, `preparer`
  (falls back to requester), `location`, `startDate`, `finishDate`, `description`, `title`, `projectType`,
  `money.classification`, `budget.budgeted`.
- Rules carry `severity: block|warn` and may return `pending` (a fact the tool has not been given yet): existing
  `breakup_equals_total`, `budget_amount_when_budgeted`, `supplemental_needs_original`, `finish_after_start`,
  `quote_present`, `quote_covers_estimate` (block at 0.70, Q34, waivable with a reason), `cost_center_active`;
  new `classification_declared`, `classification_exclusive` (CapEx and Cloud CapEx never both), `cloud_tree_consistent`
  (answers vs outcome — `cloudTree.js`), `lines_sum_to_total`, `start_not_past` (warn), `fiscal_year_matches_start`
  (warn), `single_year_span` (warn), `charge_to_owner_named`, `duplicate_open_request` (warn), `supplemental_original_exists`
  (pending), `budget_pot_available` (warn).
- `validate(a, ctx)` → `{ok, blocks, warns, pending, byStep, sections, band}`; `ctx = {matrixRow, today, openAfes, ios,
  pots, waivers}`. The wizard shows blocks inline per step, pending as facts still to come, warns as advice.

### 5.4 Red flags and the FA digest — `redFlags.js`

`computeRedFlags({afe, routing, envelope, matrixRowNow, ctx})` merges, at read time: (a) rule blocks/warns/pending;
(b) **matrix drift** — for each `matrix` recipient compare the snapshot's name with the current matrix at that level →
block "signed by X; matrix now names Y — capture Y's email approval", cleared by `fa.driftAck` with an `email_approval`
attachment; (c) envelope verification — API recipients vs snapshot (`miss`, `mismatch`); (d) SoD exclusions with no
stand-in; (e) quote coverage below 0.60–0.70 as warn. `buildRedFlagDigest(afe, flags)` is deterministic (like
`aucReview.buildPack`). `POST /fa/afes/:id/red-flags/draft` writes an outbox row `kind: red_flag_digest, status: drafted`
and returns an `.eml` (`X-Unsent: 1`) now, a Graph draft in the shared mailbox later. **No send path exists for that kind.**

`faJudgment.js` holds Judithmelanie's judgmental rows as data: asset vs expense · amount reasonable for the type ·
classification agreed · no open IO duplicates it · order type Z002/Z005. Presence checks are gone — the wizard did them.

### 11.1 The AI position, reversed on 2026-09-14

The 2026-09-04 position was *no AI anywhere*, taken so the security review had nothing to argue
with. Shashank revised it three days after the meeting: the point of the tool is to run the Fixed
Assets team's own validations once, at source, so their work shrinks to skimming and confirming.
That goal does need a model for the parts of the work that are genuinely probabilistic. It does
not need one for the parts that are rules, and it must never let a wrong machine guess travel
through an approval chain unnoticed.

So the boundary moved rather than opened. Deterministic work stays deterministic code — routing,
thresholds, segregation of duties, drift, reminders, stamping, the hand-off, every email and the
form itself. A model is used only where a person is today doing pattern recognition on
unstructured input, it produces a **proposal with a confidence** rather than a value, a person
confirms it before it counts, the proposal and the confirmation and any override are all in the
audit, and every capability sits behind a flag that ships off. `docs/architecture.md` §16 is the
full statement and is what the security review reads first.

Two asks were declined outright. An agent that approves, sends back or changes an AFE's state on
its own contradicts the whole design, which is that a person decides and the audit says who. And
LangSmith tracing would send prompts and documents to a third-party service — App Insights and
Azure AI Foundry do the same job inside the tenant. Two more were parked rather than refused:
answering approvers' questions from the AFE content, and suggesting the asset-versus-expense
answer. Both are useful and both put AFE content through a model, so they wait until the quote
reader has proved itself in front of the review.

### 12.1 Performance — the diagnosis, not the complaint

The complaint was "all clicks look like hitting server side and everything is slow". Measured
against UAT: `/api/me` 225 ms, `/api/afes?mine=1` 226 ms returning **two bytes**, and a static
CSS file **228 ms**. Server compute was effectively zero. TCP connect was 254 ms to West US
against 94 ms to a Central India neighbour. The app was never slow; it was far away, and it
asked more often than it needed to.

Both halves were fixed: the region (see `CLAUDE.md`, UAT deployment) and the round trips — four
badge calls at boot folded into `/api/me`, stale-while-revalidate so a screen you return to
paints from what it has, gzip on Node's own `zlib`, `form.pdf`'s ETag computed from its inputs
before rendering rather than from its output after, `verifyFormHash` memoised on the versions it
depends on, and a `permissionsOnly` projection for the eight route guards that only wanted
permissions. Warm request 225 ms → 37 ms; screen load 2.2 s → 278 ms; tracker payload 1,051 KB →
123 KB.

**What was measured and deliberately NOT changed.** The FA and coordinator queues build a full
projection per row, which reads as an N+1. At 2 AFEs the coordinator queue is 3.1 ms; at 152 it
is 30.5 ms — 0.2 ms a row. That is a real slope and not today's problem, and restructuring the
projection to chase 30 ms while the round trip is 37 ms would be optimising the wrong half.
Revisit it when a queue holds hundreds, and window it before de-N+1-ing it.

### 12.2 The template's own arithmetic, and two defects in it

`lib/domain/financials.js` reproduces the ` Financials (NPV, ROI & PB)` sheet formula for
formula. Reproducing it found two things wrong with it, both in the BLANK template and therefore
in every AFE built from it.

**1. The sheet reports NPV 0 and ROI 0 % for its own worked example.** Its Asset Acquisition
block has ten rows; the blank sheet fills one — 400,000 of capital, five-year life, in service
2026-03-01 — and leaves nine with a cost of 0 and no life. `Annl Depr` is `=B70/C70`, so nine
divisions of zero by nothing give nine `#DIV/0!`, which poison the depreciation total (row 107),
the taxable income (50), the tax (51), the net cash flow (53), the accumulated row (54), every
NPV column (57) and the payback fraction (58). `NPV : 10 years` is `=IFERROR(SUM(B57:L57),0)`
and `ROI %` is `=IFERROR(B62/…,0)` — so the sheet does not show an error, **it shows zero**. For
that same case the model computes NPV −297,056 and ROI −74.26 %.

A zero looks like an answer. An AFE can go through the entire approval chain carrying a
financial case that reads "NPV 0, ROI 0 %" and nobody will query it.

**2. Payback over-counts by a year.** Row 59 is
`=COUNTIF(C58:L58,0)+SUMIFS(C58:L58,C58:L58,">0",C58:L58,"<1")` — whole years under water plus
every fraction between 0 and 1. But the year AFTER the crossing also produces a fraction under
1, and it is exactly the remainder of the crossing year's: when the cash flow is level the two
sum to 1. On the Line 5 filler case in `smoke-financials` the sheet says 3.0 years and the
project pays back in 2.7. **This is the one place the module deliberately diverges**, because
overstating payback makes an investment look worse than it is, and it keeps
`paybackAsTemplate` beside it so the difference can be shown rather than argued about.

Both are for Jarrod and Judithmelanie. The second changes a figure that appears on the form.

> "Lot of white space and chips, the colour palette and no use of filling rows or cards with

| The tell | R109 |

### 12.4 One file, and a flicker that was not a repaint (R111–R114)

**R112 is the one that changes what the business receives.** "Approvers see one single PDF — not
supporting docs etc. They sign the one PDF, they can't look at multiple attachments — so append
into one single file, just like you saw all the SOWs appended in the BriCare AFE. Similarly

The tool was sending the form as envelope document 1 and every attachment as documents 2, 3, 4.
Technically complete and practically useless: an approver signing on a phone opens document 1.
Now `envelopeDocs.buildSendPackage` binds everything behind the form and the envelope carries
ONE document. `lib/pdf/bindIn.js` is the single place that does it — lifted out of
`issuedPack.js`, which was doing the same job at the other end of the AFE's life — and it gained
image pages on the way, because a facility plan arrives as a PNG.

Three things that had to be got right rather than done:

| | |
|---|---|
| **Two hashes** | `formHash` stays over the form's own bytes, so `verifyFormHash` still answers "did anyone edit the AFE after it was signed?". `packetHash` is over the file that went out. One hash over both would have fired a tamper alarm every time an attachment was added |
| **The merge decision is frozen** | The form's Documents page prints "Bound into this PDF" beside each file, so WHAT was bound is part of the page the hash was taken over. `envelope.boundDocumentIds` freezes it, like the chain — otherwise attaching a quote tomorrow makes yesterday's signature look tampered |
| **Nothing is dropped** | A file that cannot go inside — not a PDF or an image, over 25 MB, encrypted, corrupt — comes back listed with the reason and is sent as its own document. A reader always meets the whole set |

**And the demo's quote fixture was 193 bytes of valid-but-blank PDF.** Rasterising the first

the source page was empty. `seed-demo` generates a real three-page quote now, because a blank

**R111 — the flicker was never a repaint.** "The flickering of the entire screen (sideways) keeps

The same screen was "such a monochrome black and white screen", and the cause was specific: the
only filled objects on it were black. The selected answer in a toggle is the brand green now,

**R113 — "either Janine Barad or Gabriella Rafter" is ONE signature.** The $1M technical accounting

| | |
|---|---|
| **No sign of life** while the document assembles — a white rectangle that cannot be told from a broken one | `.pdfwrap` carries an "Assembling the AFE" state behind the frame, cleared by a capturing `load` listener (`load` does not bubble) |

### 12.6 The review screen, laid out as a decision (R116)

"The review screen is what catches most of the attention from the FA team. This screen is the

|---|---|

### 12.7 Readable, and then alive (R117)

**"The readability of the font (mostly due to light grey colour) is really hard."** `--muted`
carried most of the writing on every screen — hints, captions, section labels, the second line of
every row — at 5.10 against white. That passes AA at the letter of it and reads faint at 12px.
The whole secondary scale moved one step darker: ink 15.9, ink-2 11.8, ink-3 7.9, muted 6.3, and
`--deco` stopped being decorative-only at 4.9. **Nothing on a screen is under 4.5 now**, which is
a stronger statement than design rule 8 asks for.

Three more, each a small thing in the wrong place:

| | |
|---|---|
| The open-in-new-tab link was beside the heading | It is on a strip along the frame's own top edge, because that is where a reader who cannot make the page out looks for it. It cannot go INSIDE the frame — the browser's PDF toolbar owns that row |
| The cost centre and the classification were dot-separated grey text | They are chips with glyphs: cost centre amber with coins, division blue, classification, location, the signature count. Grey dot-separated text is what you write when you do not want something read |
| "N things to fix first" was a number you had to go and hunt for | It is a button: it scrolls to the first blocking message and rings it (`motion.bringTo`) |

**And motion, with no library.** The ask allowed one; the ADC rules forbid a frontend package and
this needed none. `public/js/core/motion.js` is the Web Animations API and CSS: figures count up,
buckets and chain steps and financial figures arrive in sequence, the save chip bounces when an
answer lands, and **pressing Send flies the document away as a paper plane** — started after the
request so nothing waits on it, and cancelled on a failure, because an animation that keeps
playing over an error is a lie. One hook (`afterPaint`) called by the router after every screen,
so a new screen gets it by using the shared marks rather than remembering to.

`prefers-reduced-motion` is honoured everywhere: every function takes the end state at once and
the interface still says everything, it just stops moving.

**One bug found doing it, and it is a trap worth knowing:** an ATTRIBUTE cannot be interpolated
through the `html` tag. `esc()` turns `"` into `&quot;`, so `${`data-count="${n}"`}` renders as
visible text rather than an attribute. Interpolate the VALUE instead. (`${ready ? "" : "disabled"}`
survives only because the word has no quotes in it.)

### 12.8 One journey, one chain, and a heading that is a heading (R118)

**"The new steps didn't make it to Send back."** Three screens can send an AFE back to its
author — the approver's decision screen, the coordinator's, and Fixed Assets' judgment screen —
and each asked WHERE to reopen it with a row of chips. That row was a **literal**, typed out
three times:

```js
[["1", "What"], ["2", "Who pays"], ["3", "How much"], ["4", "Why"], ["6", "Quote"]]
```

Cloud CapEx (step 5) had been in the wizard since Stage 1 and Financials (step 8) arrived with
R94, and neither reached any of the three. So an approver who could see a wrong NPV on the form
in front of them had no way to send the AFE back to the step that produced it — on every screen
that can send one back, for the whole life of the feature. Nothing failed; the list was simply
shorter than the journey, and a copied literal does not report that it has gone stale.

The journey has one definition now — `refData.WIZARD_STEPS` in the order a requester meets them,
with `REVIEW_STEP` kept separate because you cannot reopen an AFE at its own review. `/api/refdata`
carries it, `parts.reopenPicker` renders it, and all three screens call that. The wizard keeps its
own copy, deliberately: those numbers are its URLs and its `S.step` comparisons, and collapsing
them into one module would couple a screen's routing to a reference table. **`smoke-boot` holds the
two together instead** — ten checks comparing the served list against the wizard's own
`STEP_LABELS` and `STEP_ORDER`, asserting the same labels, the same order, that Review is not
offered, and that no screen still carries the literal. A copy that is checked is not a duplicate.

**"The 'Where it is' screen is so cluttered."** The coordinator's chain listed seven rows for five
people. A person named at several matrix levels signs once at the highest row, and the lower rows
come back `skipped` with `signsAs` pointing at the live one — which the screen drew as full rows.
So Udarsh Atwal appeared twice and Vrishti Aguirre appeared twice, and two of the seven rows were
saying "this row is not a row". The fact still travels and reads better where it is:
**the row that does sign says which other levels that person holds** — "Senior Manager · also
holds M1" — which is the thing a coordinator needs to know, in one line instead of two. And what
every matrix row had in common was the back half of every explanation: "cost centre 30145,
$100,001 – $300,000", five times. It is a caption over the list now, the same move the review
screen made in R116.

**"Why are all section titles always completely grey? Even the glyph."** They were: `--ink-3`
words and an `--ink-3` mark, on every panel of every screen, so a page of headings read as one
texture and none of them led anywhere. The words went a step darker — a heading is a heading —
and **the mark carries the section's own hue**, from the same family the nav uses, so the two
read as one system. Green is the default because most sections are the thing itself; a tone is
set where the section means something else: what they sign is blue, the note to approvers amber,
exceptions red, and "reopens at" red with a back glyph. The words stay ink deliberately —
colouring those would fight the content underneath, and design rule 8 is measured on text.

### 13.2 What the data already held, and nobody was showing

Two of the biggest wins cost almost nothing, because the material was already in the browser.

**The in-service date has been re-forecast twenty-two times.** `esdHistory` arrives *structured* —
one entry per revision, the seed builder splits it properly at `build_seeds.py:122`. The order
page rendered `.slice(-1)` of it as a single yellow chip and threw the rest away. One seeded
order carries sixteen promises spanning three years; `parts.slipChart` draws them as a step line
against today, and the screen now says **"16 promises on file · the date has moved 638 days
later"** — which is the most useful sentence anyone can read about an AuC line, and it was
already in the payload.

**The follow-up history is a thread.** Seven lines earlier in the same import
(`build_seeds.py:130`), the adjacent column is taken as ONE comment body per line. Measured:
816 comments, **548 carrying an `M/D/YYYY` date prefix**, and the longest holding **thirteen
dated entries in 3,249 characters** — rendered as a single text node in a 380px rail, with no
`white-space: pre-wrap` anywhere in the stylesheet, so even its newlines collapsed.
`lib/domain/reconNotes.js` splits it back: 816 bodies → **1,583 entries, 1,244 dated, 0 lossy**,
with real authors (K.K. 278 times, Yvonne Sidhu, Mark Partida, Shawn).

**The contract is losslessness, and it is tested against every real body in the seed** — a parser
that silently drops a sentence from a decade of reconciliation notes is worse than no parser.
Anything that does not parse stays as one entry; text before the first date keeps its place; a
status word like "Excluded" is never mistaken for a person's name.

It is a **regex over an extract, not a model**: deterministic, the same input always giving the
same entries, on the safe side of non-negotiable #1 because nothing it produces is a proposal or
a decision.

### 13.3 The SAP screen, which is where the complaint was loudest

`sapSheet.buildKo01` had always returned `{ screen, field, value, note, required, system }` rows —
a field-by-field sheet with a Copy on every value. `buildSteps` returned `lines: [...prose]`. So
KO01 was a run sheet and everything after it was a manual, and the difference had never been
noticed because both rendered under the same heading.

Every one of those prose lines was a field and a value:

```
"Distribution rule: Category FXA (full settlement), Receiver = the new AUC, 100%."
  → { field: "Distribution rule", value: "FXA" } { field: "Receiver", value: "169006773" } …
```

The steps now carry what earlier steps produced, so KO02 names the real AuC number rather than
"the new AUC" — the difference between an instruction and a value you can copy. The screen is
two columns, *In SAP, key this* and *Then record what it gave you*, with the capture **inline
rather than behind a modal**, and one step open at a time because one transaction is.

The person doing this is alt-tabbing between two windows. That is the whole design brief, and
the old screen was written as though they were reading it.

### 13.5 The financial case, brought to life (R131)

Raised straight after §13 landed, about the requester's Financials step rather than the back
office: "this new screen is also visually very unattractive… very black and white — why would it
be seen as 'better than editing in excel'? Also, should it be mentioned somewhere that in the
previous step, the number mentioned was X which can help you fill this step?"

**The visual half had the same shape as §13.1: the screen knew the answer and did not say it.**
`finSummary` toned a figure green when it was good and left it plain otherwise — `.kpi .v` has a
`.green` and a `.blue` and no `.red` — so an NPV of −$94,367, an ROI of −78.64%, a payback
"beyond 10 yrs" and an IRR of −35.7% all rendered in the same ink as a healthy project. Four
figures that decide whether something goes ahead, drawn as four neutral facts.

Now the screen states the verdict in a sentence before the numbers that support it, each figure
carries its own tone, glyph and sub-label ("discounted at 10%", "never, on these numbers",
"clears the 10% hurdle"), the grid's four sections sit on four grounds, and **the year the
accumulated cash flow crosses zero is marked green in the Accumulated row** — which is precisely
the thing a spreadsheet makes you find for yourself, and the best one-line answer to "why is this
better than Excel".

**The second question turned out to be a defect, not a convenience.** Three numbers on this step
have to agree and nothing was comparing them:

| | On the screen that prompted this |
|---|---|
| What "How much" asked for (`money.capexUsd` + `cloudCapexUsd`) | $140,000 |
| What the grid spends (`financials.capexRows`) | **$120,000** |
| What the assets depreciate (`financials.assets[].costUsd`) | $140,000 |

The model takes its outflows from the grid and its depreciation from the assets, exactly as the
template does, so a $20,000 gap between them is silently wrong in every figure above. `finCarry`
puts the three side by side and marks the ones that differ; matching them moved the NPV from
−$94,367 to −$114,367, which is the size of the error that had been sitting in plain sight.

**"Match them" only ever edits the two lists this step owns.** It never touches `money.capexUsd`:
that figure is the AFE's own ask, it is what the approval chain is built on, and a financial model
is not allowed to quietly rewrite the amount being requested. If the ask is wrong, it is wrong on
the step that collects it.

**And depreciation is drawn rather than described.** "Depreciates at $24,000 a year, half of that
in 2026 and in the year it leaves" is a sentence about a shape; the shape is a short bar at each
end with full bars between, and it renders in 30px with the year and the amount on each bar.

### 13.6 One AuC, one chart, one thread — and a workbook that needed telling (R132)

Shashank, on the order page: "the sections are repeating thrice for the instance I attached. Is
that real text blob duplicated multiple times or is it an app glitch?"

**Both, in different parts.** The DATA is real: the recon extract carries one row per GL account,
so IO 310480 legitimately appears three times under AuC 169005554 —

| GL account | | Balance |
|---|---|---|
| 169005 | CIP_Furniture & Fixtures | $12,277,040.45 |
| 169050 | CIP_Manual Furniture & Fixtures | $0 |
| 169055 | Manual CIP-Machinery | **−$24,123** |
| | **Total on this AuC** | **$12,252,917.45** |

The PRESENTATION was ours. Each row was drawn as a full block, so the number, status, age,
reviewer and owner — identical on all three — were repeated three times; the date chart and the
follow-up thread were drawn three times over, because they are byte-identical across the lines of
one AuC; and the one thing that actually differed, the balance, appeared as three separate facts
with **no total**. So the AuC's real balance was nowhere on the screen, and a negative GL line sat
in the middle where nobody would look twice. Identity once, the GL lines as rows, and the sum.

**Then the labels on the chart found a defect in the workbook.** Asked to put the dates on the
nodes, one label came out as "Oct 5" — because IO 312103 carries `"10/31/225"`, a dropped digit
from 2025, which `Date.parse` reads as the year **225 AD**. One such value stretches the axis
across eighteen centuries and squashes every real promise into a sliver: the V-shaped dip in that
chart, which had been accepted as "the date moved earlier then later", was entirely this typo.

Across the extract there are **47 unreadable dates on 38 of the 528 lines** — `"Q3 2023"`,
`"#3_11/30/2025"`, `"7/31/2025_2nd"`, `"06/30/226"`. They are dropped from the line and the scale
and **named underneath the chart**, because only the FA team can correct a number in their own
file, and silently discarding it would guarantee they never do.

A second date bug came out of the same work: `Date.parse("2025-05-15")` is UTC midnight and
`Date.parse("5/15/2025")` is LOCAL midnight, the file uses both, and reading either back with the
UTC getters put every US-format date **a day early**.

**And a node is now a control.** Clicking one jumps to the follow-up entry nearest that moment and
rings it. It is temporal navigation, not a causal claim: the estimated-service-date column and the
comment columns are different columns, and testing showed only **8% of promises are mentioned in
an entry's text at all** — so where the date IS named that entry wins, and otherwise the nearest in
time does. Building the "obvious" causal link would have been fabrication 92% of the time.

Two smaller things: SVG text scales with the viewBox, so the chart's 9.5px labels rendered at
5.4px on a phone (a media query compensates for the scale); and the review chip now names its
quarter from `aucReview.periodOf`, because a chip that says "this quarter" is still saying it in
October about July's population.

### 13.7 The issued AFE, said as a structure (R133)

### 13.8 Where Fixed Assets actually writes, and who gets to look (R134)

Three things, all from the same session and all about the issued AFE.

**The marks go at the top of page one.** "The Issued by Fixed Assets and Budget / Actual /
Commitment are placed below rather than on top of the AFE form — refer attachments of both, your
generated vs what FA gave for BriCare." The worked example is unambiguous: the AuC number is
written in red in the top-left margin and the SAP table is pasted into the top-right one, both
above the form's own grid. There is room for it on every AFE — the template's `DOC_HEADER` only
occupies x 18-180 — so nothing is drawn over the form and nothing the template prints is covered.

The first attempt got it wrong in exactly the way the brief warned about: a hard-coded band floor
of 746 put the table straight through "AUTHORITY FOR EXPENDITURE", whose rectangle runs 740.6 to
750.4. **The floor is computed from the layout's own rectangles now**, so a regenerated template
can move and this still cannot collide with it. Rasterised and looked at, per the repo's own rule —
measuring the drawing operators would have passed the overlapping version.

It cannot affect the form hash: `verifyFormHash` re-renders without `issued`, so these marks exist

### 13.9.1 The performance pass

Asked to make it faster after eight rounds of changes, the measurements said it was not slow.

| | Local | UAT (50 ms round-trip floor) |
|---|---|---|
| `/api/me` | 14 ms | 46 ms |
| `/api/fa/queue` | 14 ms | 150 ms |
| `/api/tracker` | 33 ms | 198 ms |
| Screen render | 15–83 ms | — |
| Tracker keystroke | 12–17 ms | — |
| Long tasks (>50 ms) | **none, on any screen** | — |

UAT is several times slower per core because it is a **B1** App Service, which is the tier and not
the code. Nothing in the render path is pathological.

**But the measuring found one real defect, and it had been there since R92.** The gzip middleware
wraps `res.send`; `express.static` streams through `sendFile` and never touches it. Every API
response was compressed and **not one static file was**: `app.css` was leaving UAT at 114,346

`app.css` now goes over the wire at 28,079 bytes instead of 114,346. `Cache-Control: no-cache`
is untouched, deliberately: the module names are not hashed, and long-caching them is what
shipped a screen built from two incompatible halves on 2026-09-18.

### 13.12 A stepper segment goes somewhere (R139)

### 14.3 A send-back lands with the person who raised it (R147)

> "At any workflow, if it gets rejected, it should go back to the project manager's bucket,
> whoever raised the initial AFE." (Jarrod, Meeting #6)

The bucket was already right: a returned AFE sits in the requester's own *Needs you*. What was
wrong was everything that said whose it was.

- **`returnedTo` recorded who sent it back and not who it was for.** It now carries `to` —
  the requester, always — beside `role` and `byName`. `role` is untouched: it is who sent
  it back, and `submit`'s signatures-stand shortcut reads `role === "fa"`.
- **The mail had three equal addressees.** `ownerSideEmails` wrote one row each for the
  requester, the preparer and the coordinator, so the coordinator — the one person on the
  owner side who did not raise it — was told it was theirs exactly as loudly.
  `ownerSideMail` writes ONE row: the requester addressed, the others copied, and never the
  person acting. When the actor IS the requester the next of them is addressed, so the mail
  still reaches somebody.
- **The FA judge screen said "Send back to the coordinator"** whenever the division had one,
  and the approver's sheet named nobody. Both name the requester now and say who is copied, in
  the sheet that sends it.
- **A decline is told the same way.** Jarrod said "rejected", and a decline is the rejection.

The history names the person too — "Fixed Assets sent it back to Shashank Srivastava" —
from `toName` on the audit row; rows written before it read "the requester", which was always the
intent.

**This decides whose it is, not who may touch it.** Anyone on the owner side still fixes it and
resubmits; Jarrod's point was about whose queue it lands in and who is told.

`question`, `withdraw` and the approval notice still address the owner side as before: none of
them is a rejection, and the question thread is §2.4's to redesign (R149).

### 14.4 A send-back keeps the signatures when nothing that decides the AFE changes (R148)

> "If they need to redo this entire approval workflow, it would be a real challenge for the
> requester… it will delay the process." (Judithmelanie, Meeting #6) Jarrod: "if any critical information
> is getting changed… ideally it should go for re-approval." Imogen drew the line: the amount, the
> cost centre and "budget change" matter; the start date, the end date and the description do not.

This answers **Q38** ("does send back reset every approval?"), which had stood since the v0.3
document with the default "send-back voids". The answer is: it resets nothing unless something
that decides the AFE changes, and then it resets everything, because a new round is a new
decision.

**The decision moves from the send-back to the resubmission.** A send-back mid-chain used to void
the envelope on the spot, so the question "did the fix matter?" was answered before the fix
existed. Now the round is **paused** (`routing.status: "returned"`, the holder's row `returned`)
and `lib/domain/resume.js` decides when the AFE comes back. The check is pure, and the view carries
its answer (`view.resume`), so every screen that shows a returned AFE says what resubmitting will
do before anybody does it, and the answer moves as the requester edits:

| It goes straight back when these are unchanged | Because |
|---|---|
| The money: cost centre, classification, the four amounts, the cost lines, the charge-to, the requester, the kind | `financialFingerprint`, frozen at send; Imogen's list |
| The budget and the case: budgeted, the pot, its category and fiscal year, NPV, IRR, ROI, payback | Imogen named the budget; an approver can send an AFE back to the Financials step, and resuming after the NPV moved would ask the next signer to sign the wrong one |
| Who signs: the chain rebuilt now, by person and order, and who is copied | A signer the coordinator added while it was back has to be on the envelope |
| The supporting documents: `envelope.supportingDocumentIds` | The envelope's document cannot change once somebody has signed it, so a quote added while it was back would be a quote nobody signed over |

Everything else, the description, the dates, the scope, the justification, is text, and resumes.

**`caseFingerprint` is kept apart from `financialFingerprint` on purpose.** The latter is frozen
on every routing already sent; adding the budget to it would have made every AFE in flight look
changed, and every Fixed Assets return on those AFEs go round again. A round sent before R148 has
its case snapshotted when it is sent back or returned by Fixed Assets instead, which is the last
moment nobody could have edited it.

**Submit and Send decide the same way.** The coordinator's Send on a returned AFE opened a new
round every time, including after a Fixed Assets return where the requester's Submit would have
kept the signatures. The same AFE kept or lost its approvals depending on who pressed the button.

**The honest consequence, to say out loud in Meeting #7.** A resumed round is the SAME envelope,
so its document is the one first sent: the fix is on the AFE, not in the file the remaining
signers sign. That includes the approver who asked for the fix. The tool says so where it matters.
The next signer's screen names who resubmitted it, what changed (compared with a snapshot taken at
the pause, so an amount typed and put back is not "changed") and whose signatures stood, and the
same goes into their mail. The audit row carries `resumed`, `kept` and `changed`. Fixed Assets
meets the edit as the explained form-hash warn it already gets after its own returns. This is what
Judithmelanie asked for ("once they are approved, that approval is sufficient"), and it is an audit
judgement, so it is theirs to confirm. The three options, for Meeting #7:

1. **As built**: resume whenever nothing that decides it changed. Nobody re-signs; the remaining
   signers sign the document as first sent, and the fix is on the record.
2. **Stricter**: any send-back mid-chain goes round again (Q38's old default), and only a Fixed
   Assets return keeps its shortcut, because there nobody is left to sign. This is one condition
   in `resume.js`. (The plan's own "resume only when nobody has signed yet" is not worth offering:
   with no signature to keep, a new round loses nothing and gives the signers the corrected file.)
3. **Richer**: a new envelope for the remaining signers only, with the earlier approvals printed on
   it. The remaining signers see the fix, but two documents exist for one AFE, which breaks "one
   document for everyone until the last signature" (R156), so it is not the default.

**`document.pdf` had the same round problem, and it was older than this.** It served the latest
file of each kind. On a returned AFE about to go round again, that was round one's packet under a
heading saying "as it will be sent". During the whole of round two after a Fixed Assets return, it
was round one's SIGNED set, because a completed round's signed set is never taken off the AFE. It
resolves by the round that covers the AFE now: the issued pack, else the current envelope's signed
set once complete, else the packet it went out with, and before anything has gone out, or on a
returned AFE that will go round again, the packet a send would build. `smoke-fa` now fails on the
round-two case, which the old code got wrong.

**The live DocuSign path, and what is not known yet.** While a round is paused the envelope stays
out in DocuSign. The poll job leaves a paused envelope alone rather than record a signature on an
AFE that is not in approval (the transition would refuse it after the envelope had already marked
it seen, and it would be lost). On resume it re-reads the envelope whatever its look-back window
says (`envelope.reconcile`), so a signature or a decline given in DocuSign during the pause lands
then, in order. **Two things to settle once there is an integration key**: DocuSign keeps sending
its own reminders during a pause, and a long pause can run into the envelope's expiry. DocuSign's
workflow pause may answer both; it has not been tried, so it is not claimed here.

**What did not change.** `withdraw` and `decline` still void at once, and a send-back from
`submitted`, where no round is in flight, closes whatever it has, as it always did.
`FORM_LAYOUT_VERSION` stays 4: nothing the form draws moved.

### 14.5 A conversation Fixed Assets can use, instead of a rejection (R149)

> "Instead of hard rejection… let's use the comment section only. Better to avoid Teams or
> emails. It will have the audit trail — what we asked and what they responded." (Jarrod, Meeting #6)
> "We need written information in the AFE for documentation proof." (Imogen)

**There was nowhere to write it.** The only conversation in the tool was the approver's
question-and-answer pair: the holder's alone, only while the AFE is in approval, and it puts the
AFE on hold and pauses the approval clock. None of that means anything once Fixed Assets has the
AFE, so Fixed Assets had two choices, send it back or leave the tool, and both are what Jarrod was
asking them not to do.

**`comment` is a transition that changes no state.** It goes through `applyTransition` like
everything else, so it is guarded (anyone who can view the AFE, while it is alive:
`refData.COMMENT_STATES`), audited with its full text, and listed in the history. The audit row is
the "what we asked and what they responded" Jarrod wants on the record.

**Who hears it.** Everyone in the conversation except the author, in at most two mails, because
the two sides open the AFE on different screens:

| | Told | Link |
|---|---|---|
| The owner side | ONE mail: the requester addressed, the preparer and coordinator copied (R147's shape), never the author | the AFE's record |
| The other side | everyone off the owner side who has spoken **at the stage the AFE is at now**, plus, when an owner writes, whoever holds it: the approver with the envelope, or Fixed Assets' shared mailbox once it is theirs | the screen they work on |

"At the stage it is at now" is the refinement that stops a comment in Fixed Assets reaching the
approvers who sent the AFE back weeks earlier. Every thread line now records its `side`. A line
written before that is read by what it carries (a recipient id is an approver's).

**Where it shows.** `parts.thread` is one component, with a compose box. The same markup was
hand-written three times (the approver's decision, the coordinator's routing, the requester's
record), and the FA judge screen had none. It now sits under whichever tab is open there.
`core/comments.js` is the one function that posts. A comment from Fixed Assets or an approver puts
the AFE in the requester's **Needs you** ("1 with a comment for you", `afeBrief.talk`), because a
question that moves nothing is still a question put to you. The FA queue says **"Shashank wrote"**
when the requester side has answered.

**Decided: comments only for Fixed Assets.** The plan left open whether Fixed Assets also needs the
formal question/answer. It does not. That pair exists to pause an approval clock, and Fixed Assets
has no clock to pause. A hard rejection stays `fa_return`.

### 14.6 Equipment from Acme's own inventory, screenshots, and the quarter-end filter (R150—R152)

> "At quarter end… fifty AFEs… fifteen of them are internal. If I can apply a filter, that can
> ease out my work." (Imogen, Meeting #6)

**A whole class of AFE the tool had never met.** Equipment moved out of Acme's own inventory is
not bought, so there is no vendor quote. It carries a quotation Acme itself generates and a
screenshot of the material as SAP displays it. The worked example is AFE **313147** (QX700 ddPCR
instruments, Site H), whose cost line is the material number `12025219 - QX700 ddPCR System`.
Imogen first described the quotation as a "Acme code"; it is a second kind of quote, not a new
field, and that correction shaped the design.

**One question on the Quote step decides it.** *Where does it come from?* An outside vendor, or
Acme inventory. `afe.sourcing` is a FIELDS row, asked of exactly the AFEs the 925 surplus
question is asked of (something physical, not software), and reported in `validation.applies` so
the wizard paints the server's answer. It is **optional with a default of vendor**, not required.
A required field would have raised a block on every tangible AFE already in flight the moment it
was re-validated, which at Fixed Assets is a red flag nobody could clear.

| | An outside vendor | Acme inventory |
|---|---|---|
| What prices it | a vendor quote or SOW (`quote_present`) | a Acme quotation (`internal_quote`) |
| What else is needed | nothing | a screenshot of the material in SAP (`material_evidence_present`) |
| Quote coverage | the vendor quote's total | the Acme quotation's total, with Acme already filled in as the vendor |
| On the form | unchanged | a "Sourced from: Acme's own inventory" row on Project Details, and both documents on the Documents page |

**The roles are one list now** (`refData.SUPPORTING_ROLES`, `QUOTE_ROLES`). "Quote or SOW or backup"
was typed out in about a dozen places, in the rules, the form, the binder, the issued pack, the
wizard, the approver's page and the Fixed Assets screens, and a new role would have reached some
of them and not others. The browser gets the lists with the rest of `/api/refdata`.

**R151: a screenshot is a document.** Every role takes a PDF, a PNG or a JPEG. The server sniffs
the bytes, as it always did; the binder gives an image a page of its own in the file the approvers
sign. The Quote step's badge is the document's own (`parts.docBadge`), not a hard-coded "PDF".

**`FORM_LAYOUT_VERSION` stays 4, and that is a measured decision, not an omission.** The plan said
to bump it because the Documents page gains two roles. So every AFE on hand (the demo set, and the
AFEs the Fixed Assets and envelope suites leave behind) was rendered twice, by the committed code
and by the new, exactly as `verifyFormHash` renders. The bytes were identical for all of them, and
the committed code's renders matched the hashes stored at send, so the comparison is sound. No AFE
already signed can carry the new roles or the new row. A bump would therefore have raised a
"layout changed" warning on every AFE in flight for a change none of them shows. Rasterised, the
Project Details page of an inventory AFE prints the row and both documents, and the screenshot
binds in as a page of its own.

**R152: the filter.** `afeBrief.sourcing` (null where the question does not apply), `?sourcing=` on
`/afes`, `/projects` and `/tracker`, a chip and a search on the projects list and on the tracker,
and a `Sourcing` column **appended** after Aiden's own columns in the projects CSV (the tracker's CSV
has one too). A tracker line comes from the recon workbook, so it knows where its equipment came
from only when the tool issued its order. A line that predates the tool says nothing, rather than
guess.

**Still wanted from Imogen:** the Acme quotation and the Display Material screenshot as they
really look, to confirm the two upload slots ask for the right things. `AFE with Material
Screenshot.pdf` carries them only as images with no text layer.

### 14.8 One document, all the way to the end (R156, completed)

§14.1 made `document.pdf` the one document and fixed the signed set losing its attachments.
Two things were still true of it afterwards, and both contradicted "post FA finalization also,
the document remains untampered (no different versions)".

**1. The issued AFE was a new drawing, not the signed file.** `issuedPack` called
`renderAfeForm({ issued, stamped: true })`: the form drawn afresh from the AFE as it stood, with
the tool's own picture of the signatures on it and the attachments re-bound behind. So:

| | What it meant |
|---|---|
| An edit during a Fixed Assets return that let the signatures stand (R148) | shown in the issued AFE, which nobody signed |
| A form layout change between signing and issue | the issued AFE redrawn in the new layout |
| A live DocuSign envelope | DocuSign's signatures replaced by the tool's drawing, against non-negotiable #3 |
| A supporting document that was opt-in (a backup) | inside the signed AFE, missing from the issued one by default |

Now the pack **is** the signed file, which is what the FA team make by hand today:

1. the newest `envelope_pdf`, copied page for page;
2. Fixed Assets' marks drawn over page 1 by `afeForm.markIssued`: the red band, the SAP table in
   its box, and the order number in the AFE NO cell. pdf-lib puts the page's own content in a
   saved graphics state before drawing, so the signed content is untouched;
3. one index page, "Added by Fixed Assets", saying which pages are the signed ones and where
   each addition is;
4. what Fixed Assets add: the certificate and their evidence by default, plus any supporting
   document the signed set does not carry.

**Nothing inside the signed set is bound twice.** Completion now records `carries` (which
documents are inside) and `pages` on the signed set. For DocuSign that is everything on the
envelope, and the combined PDF is fetched with `certificate=false` so its contents cannot depend
on an account setting. A signed set from before this change is worked out: until R156's fix the
simulation stored the form alone, and the packet is always longer than the form whenever anything
was bound in.

The send sheet shows the signed AFE as a fixed block with its contents inside it. Only what goes
behind it has a checkbox.

**2. The Documents panels listed four generations of one document.** The requester's record, the
coordinator's frozen view and the Fixed Assets judge screen each listed the generated form, the
sent file, the signed set and every issued AFE as separate rows. Now:

- one row, **The AFE**, opens `document.pdf` and names the stage (`parts.theAfeRow`);
- then the certificate and what people attached (`parts.ownDocuments`);
- a rebuilt issued AFE **supersedes** the one before it (`supersededAt`, `supersededBy`). The old
  one is kept and never deleted, the same discipline as a routing round.

`showMe` falls back to `document.pdf` rather than to a stored generation. The issue screen's
"Open the signed AFE" also points at `document.pdf`.

**Proof** (`smoke-fa`, at the level of the PDF):

- every signed page's content streams are carried byte for byte;
- page 1's own streams appear intact, with the marks after them;
- the quote is inside the signed set and is not bound a second time;
- the page count is signed pages + index + the screenshot's own page + what was added;
- a rebuild is byte for byte the same document and supersedes the first;
- `document.pdf` serves the newest.

Rasterised, page 1 shows the signed form with its signatures, the red band and the order number.
The SAP table sits in its box when it fits and takes its own page after the index when it does not.

**`FORM_LAYOUT_VERSION` is unchanged.** None of this reaches a render that is hashed: the marks go
onto a copy of the signed page, never into `renderAfeForm`.

proposal nobody confirmed cannot count for anything. (The architecture document's older rule that a

### 16.9 The database signs the app in with Entra ID — built, inert (Part B)

DB Ops' request of 2 October. With `DATABASE_AUTH=entra` each new connection presents a token from
the app's identity for `https://ossrdbms-aad.database.windows.net`, the pool is built from discrete
fields (a connection string would override the token with an empty password) and the server's
certificate is verified. The boot DDL runs only when `to_regclass` finds a table missing — proved on
Postgres 16: a read-write-only role cannot run `CREATE TABLE IF NOT EXISTS` even when the table
exists ("permission denied for schema public"). `/health` reports `storageAuth`; `POST
/api/admin/db/entra-check` dry-runs the switch inside the container — token, certificate, sign-in,
privileges — and changes nothing. The runbook (Entra admins, the role, the grants, the switch, the
password off, the old server's dump and deletion) waits on access, one confirmed step at a time.
